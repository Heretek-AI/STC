## 1. Community feedback on existing orchestrators

The corpus is source-verified; community sentiment is not in the corpus, so it came from primary search. Treat as directional, not statistical.

**What people like:**
- Worktrees as the answer to parallel-agent chaos — "Running parallel Claude Code agents on a single repository checkout is a recipe for chaos… Two agents trying to edit the same file at the same time produce the kind of merge conflict that takes longer to untangle than the original task." `[VERIFIED developersdigest.tech Git Worktrees + Claude Code 2026 playbook]`
- Claude Code rated highly for code quality and the MCP ecosystem. `[VERIFIED codemyspec.com review roundup]`
- The `CLAUDE.md` / skills culture — a whole cottage economy of "tips" content exists around it, which is a signal that *project memory is the thing people actually fight with*.

**What they complain about (ranked by recurrence in the sources):**
1. **Token cost compounding.** "Costs compound because context accumulates on every message." `[VERIFIED buildtolaunch.substack.com]`
2. **Subagent fan-out multiplies spend.** "Each subagent runs its own API requests in a fresh context window… Three subagents on one task is roughly four times the token spend of a single-thread session." `[VERIFIED youcanbuildthings.substack.com]` — this is a direct hit on naive multi-agent designs and a strong argument for my zero-token coordination plane.
3. **Quality instability.** A widely-cited postmortem describes a caching bug + prompt changes producing a measurable drop (~3%) that users felt as "less capable, more repetitive, weirdly terse." `[VERIFIED aiforanything.io / shattered.io postmortem roundups]`
4. **Setup and identity friction** — the entire multi-account ecosystem (`claude-code-profiles`, `ccm`, direnv patterns) exists because out-of-box profile switching means "logging out and back in, and everything else stays mixed." `[VERIFIED github.com/CarlosTheory/claude-multi-account, quinnjr/claude-code-profiles]`

**What is missing everywhere** (my synthesis of the gap between the corpus and the complaints):
- No product owns **semantic write-conflict prevention**. They all ship worktrees and accept merge pain — the community literally documents "worktrees solve this" as the *state of the art*.
- No product owns **completion discipline** (§2.10). Everyone ships "done" gates; nobody ships "refuse to accept 'done' as an answer."
- No product makes **token cost a first-class, pre-declared budget**. It is a meter you look at after, not a contract you set before.
- Creative/multimodal work is bolted on (Orkas' nine specialists, iPolloWork's six output modalities) rather than designed as first-class lanes.

## 2. Answers in depth

### 2.1 Are there other projects doing this?
Yes — 300+ catalogued in `awesome-agent-orchestrators`, of which I audited 12 at source level. The taxonomy by supervision modality: parallel terminal agents · parallel desktop/web · multi-agent swarms · autonomous loop runners · autonomous task runners · infrastructure & primitives · personal assistants.

The honest positioning: **everyone is solving "run agents in parallel and review diffs."** Nobody is solving "prevent the conflicts" (semantic claims), "make it free to coordinate" (zero-token plane), or "make them actually finish" (completion contract). Those three are Studio's whitespace.

### 2.2 Complex work: 3D, image, video, desktop, web

**The design principle that answers all five at once: artifact-first, editable-always.** Never let a creative agent return a finished binary. Return the *source of record* and render from it.

| Capability | Works today | Still unreliable | Studio's pattern |
|---|---|---|---|
| **Images (assets/marketing)** | OpenAI/Gemini image APIs, Replicate, fal.ai, Ideogram, Flux; ComfyUI headless for pipelines | Iterating a raster: models don't re-edit well | **HTML/CSS/SVG-first.** Generate layout + vector assets; raster only as a final export. Agent edits the source; re-render is deterministic. This is exactly iPolloWork's "editable production loop" `[VERIFIED iPolloWork README + specs]` and Orkas' ImageStudio "HTML/CSS/SVG first, image models when the shot needs them" `[VERIFIED Orkas README]`. |
| **Video** | FFmpeg pipelines, Remotion (React → video), narration via TTS, captions/dubbing | Long-form generative video is still weak | **Remotion/code-first timeline** as source of record; generative shots are *clips inserted into a coded timeline*. Orkas VideoStudio and iPolloWork Video views both land here. |
| **3D** | Blender `bpy` scripting, OpenSCAD, CAD APIs, text-to-3D (Meshy/Tripo/TRELLIS/Hunyuan3D) | Text-to-3D gives meshes, not editable topology | **Parametric-first** (OpenSCAD/CAD script as source of record) or **Blender-py scripts** for scene assembly. Treat text-to-3D as an *asset import*, never the source of record. `[HYPOTHESIS: a scripted-parametric 3D task completes at higher fidelity than a text-to-3D task of the same complexity, measured by editor round-trips.]` |
| **Web apps** | Playwright MCP with accessibility-tree snapshots; Browser MCP; Stagehand/browser-use | Screenshot-vision approaches are slow and token-hungry | **Structured automation first, pixels second.** Consensus of the 2026 comparisons: "the most reliable architecture is usually structured browser automation first, computer use second — use Playwright MCP when the application exposes stable semantics, and computer-use when a workflow depends on pixels, canvas, legacy interfaces." `[VERIFIED himat.tech Playwright MCP vs Computer Use 2026]` |
| **Desktop apps** | Accessibility-tree MCP servers (Windows-MCP, Peekaboo); Anthropic computer use; Cua Driver | Pure pixel control is flaky and expensive | **Accessibility-tree (AXUI / UIA / AT-SPI) as the primary surface**, screen pixels as the fallback for canvas/legacy. Gold-standard framing: "accessibility-tree-based servers… remain the gold standard." `[VERIFIED dev.to computer-use-MCP 2026]` |

**Cross-cutting:** these lanes get their own **role manifests** — a Creative agent has image/video/3D/browser tools and *no* `fs.write` to source trees; a Code agent has neither. The MCP gateway enforces it (§ prior report 3.2).

**Distro of the creative stack:** keep generators behind the same MCP gateway as **ephemeral MCP servers** (per-task, destroyed after), so a video render doesn't sit resident in every agent's tool surface — that would be the 80K-token tax from agent-swarm's measurement all over again, in a different costume.

### 2.4 Long-term project data — **is a vector DB a good idea?**

This is the best question you asked, because the community is genuinely split and the corpus answers it better than the hype does.

**Short answer: a vector DB is a retrieval *component*, not an *organizing principle*. If you start with it as your memory architecture, you get the complexity without the memory.**

The case against, from primary sources:
- "A vector database does one thing well: approximate nearest-neighbor search over embeddings… most agent-memory queries don't decompose to pure semantic similarity." `[VERIFIED hindsight.vectorize.io, The Case Against External Vector DBs for Agent Memory]`
- "For specific facts and shared state, a structured key-value approach is often more reliable and easier to maintain." `[VERIFIED n1n.ai Rethinking Agent Memory]`
- "Vector search keeps failing teams who deploy it as a complete solution." `[VERIFIED mindstudio.ai]`
- The synthesis piece: "vector search and knowledge graphs solve different halves of the memory problem… the half they are missing is the half that breaks in production." `[VERIFIED hindsight.vectorize.io, KG vs Vector Search]`

**What the corpus actually ships** — and it's instructive that the *best* memory systems are multi-modal, not vector-only:
- `oh-my-pi` `MemoryRow` carries a **statement-lifetime model**: `veracity` (stated|inferred|tool|imported|unknown), `valid_until`, `superseded_by`, `trust_tier`, `recall_count`, `scope`. Retrieval runs **four voices** — vector, graph, fact, temporal — combined into `combined_score`. `[VERIFIED packages/mnemopi/src/types.ts:9-28, core/polyphonic-recall.ts:8-33]` This is the best memory schema in the corpus.
- `claude-smart` has **no vector DB at all** in-process — it delegates to a remote hybrid (BM25 + vector + RRF) and, crucially, keeps a **citation registry** proving whether a memory was actually used. `[VERIFIED reflexio_adapter.py:440-495, cs_cite.py]`
- `munder-difflin` runs a **five-layer stack** (per-agent markdown → reflector → semantic palace → knowledge graph → visualization) and had to build a **quarantine reaper** because a never-delete bug hit **100GB in 8 hours**. `[VERIFIED src/main/palaceReap.ts:1-30]` That number is the vector-store cautionary tale.
- `agent-swarm` has the most complete embedding stack (embeddings + reranker + graph expansion + LLM raters with citation ratings) — and it is the heaviest.

**Studio's answer — the Memory Ladder (structured-first, vector as one voice):**

| Layer | What goes here | Retrieval | Cost |
|---|---|---|---|
| **L0 — Git + receipts** | every merge, every task receipt, every spec revision | `git log`, content-addressed blobs | ~0 |
| **L1 — `studio.db` facts** | decisions, ADRs, budgets, claims, typed outcomes | SQL + FTS5 (SQLite) | ~0 |
| **L2 — Markdown project memory** | `MEMORY.md`, per-scope notes, AGENTS.md | grep / FTS | ~0 |
| **L3 — Structured memory rows** | facts with `veracity`, `valid_until`, `superseded_by`, `trust_tier` (oh-my-pi model) | keyed lookup + recency | low |
| **L4 — Optional semantic index** | *only* narrative/design prose where paraphrase matters | embeddings + **reranker** | opt-in per project |

Rules that keep it honest:
1. **L4 is opt-in and scoped** — enabled per project, never global. If L0–L3 answer the query, L4 is not consulted.
2. **Embeddings are versioned and re-derivable.** Every row stores `content_hash` + `embed_model`. Model change = rebuild, never a silent stale index.
3. **Never store what `git` already stores.** This is the single biggest source of duplication in agent systems.
4. **Reranker is mandatory if you ship L4.** Raw ANN recall without reranking is where "why did it retrieve *that*?" complaints come from.

`[HYPOTHESIS: on a 30-day engineering project, L0–L3 alone answer >70% of agent memory queries correctly, and adding L4 improves end-task success by <10% while adding measurable indexing cost.]` — that's the spike that decides whether you ever turn L4 on.

### 2.5 Agents that shuttle data — the find↔return loop (deep dive)

This is where most multi-agent systems quietly fail: research results get *summarized away* and the implementer works from a paraphrase.

**The failure mode, precisely:** Researcher reads 40 files → returns 800 words → implementer acts on 800 words → the 40 files are gone. Nothing in the pipeline can check whether the implementer's claim is grounded.

**Studio's answer: the Evidence Packet, not the report.**

```
EvidencePacket {
  packet_id:      sha256(content)          // content-addressed
  task_id:        ...
  researcher_id:  ...
  claims: [ {
    claim_id,
    text,                                  // the assertion
    cites: [ { blob_ref, locator, quote } ]// file + line/span + verbatim quote
    confidence: stated | inferred | unknown,
    superseded_by: claim_id | null
  } ]
  artifacts: [ { blob_ref, mime, kind: raw|extracted|derived } ]
  open_questions: [ ... ]                  // what it could NOT find
}
```

**Six rules for the shuttle:**

1. **Cite or don't claim.** Every claim carries ≥1 `cites` entry with a verbatim quote and a locator. A claim without evidence is stored as `confidence: unknown` and cannot be used to justify a code change. (Model: claude-smart's counterfactual cite-bar — "your answer would be substantively different if the item had not been shown." `[VERIFIED cs_cite.py:69-76]`)
2. **Blobs are content-addressed and immutable.** Raw pages/files fetched live in the evidence store (`sha256`), referenced by `blob_ref`. The implementer can `read evidence://<ref>` — it doesn't need the researcher alive.
3. **Schema-first return, prose-second.** A researcher fills a typed schema (the `EvidencePacket`); any prose it writes is *decoration on the packet*, not the packet. Free-text summaries are the #1 cause of information loss.
4. **Roles are asymmetric and have different tools.** Researcher: search, fetch, read, browser. *No writes.* Implementer: read + write + test. *No browser.* Auditor: diff, AST, lint, test. *No writes.* This is the § prior-3.2 manifest table, and it's also what stops the implementer from "doing its own research" and losing provenance.
5. **Return-then-close is mandatory.** A researcher task terminates by writing the packet to the ledger — not by chatting. If it stalls mid-fetch, the packet has `open_questions` and the scheduler can resume it. This is the same completion contract as §2.10.
6. **Round-trip is a first-class task type.** Sometimes the implementer needs more; it issues a `needs_evidence` receipt that reopens a *targeted* research task with the specific gap named — not a vague "look into X again."

**Who does the shuttling?** Not a fourth "messenger" agent. The **coordination plane** moves packets — it is zero-token and cannot summarize. The only models involved are the ones producing and consuming the packet. This is a direct consequence of the no-model-in-the-loop rule.

### 2.6 Generating human feedback from a UI/UX

Three distinct surfaces, and conflating them is why agent UIs get bad:

**(a) Decision prompts — high friction, must be rare.**
ACP `session/request_permission` is the wire. The **approval inbox** pattern (from the ecosystem catalog: Calyx, octomux, intentic) consolidates every pending decision across all agents into one queue so a human isn't tab-hopping. Studio: one inbox, keyboard-first (`a` approve, `r` reject, `e` edit-and-return). Escalate to `ask` only when the role manifest says so.

**(b) Taste/design feedback — must be cheap and continuous.**
This is the hard one, and the answer is **feedback on artifacts with anchors, not free-form chat**:
- Creative output renders in the cockpit with **anchorable regions** (SVG node, video timeline range, PPTX slide). A click leaves a finding pinned to that anchor — same mechanic as hunk-level review findings.
- Findings route back to the *originating session* as a queued message (the head-SHA-fenced pattern from `agent-orchestrator`'s review delivery `[VERIFIED review.go:779-793]` — never inject feedback onto work that has already moved).
- **Preference capture is separate from finding capture.** A finding is about *this* artifact; a preference ("always dark UI, never purple") is a durable memory row. iPolloWork calls these `profiles`; claude-smart calls them `profiles`/`playbooks`. Studio: `preference` rows with `scope` (global|project|role) and the same `superseded_by` lifecycle.

**(c) Structured input forms — for exactly the moments prose is wrong.**
Orkas has an `input_channel: 'form' | 'prose'` protocol where an agent emits a form and the human fills fields `[VERIFIED Orkas agents.ts / local_agent_user_input]`. Steal this wholesale: scope negotiation, budget confirmation, and design briefs should be forms. Everything else can be prose.

**Anti-pattern to avoid:** voice/microphone control without a **distinct-token confirm**. munder-difflin documents this precisely — destructive verbs require a confirmation token that is "NEVER a bare `yes`, so ambient speech can't authorize a kill." `[VERIFIED realtimeActions.ts:12-122]`

### 2.7 Assigning and reviewing tasks
Deepened from the prior report — three additions from this pass:

1. **Assignment is a claim, not a directive.** Agents claim tasks from the queue under a lease (agent-swarm's offer/claim protocol `[VERIFIED types.ts:547-551]`), which is what makes the plane zero-token.
2. **Review has two independent axes** and most products only ship one:
   - **Conformance** — did the change match the declared write-intent? (deterministic, cheap, the immune check)
   - **Quality** — is it good? (LLM auditor, gated on the first axis passing)
   Ordering matters: conformance first. A perfect-looking diff that touched undeclared files is a rejection, not a comment.
3. **Feedback is delivered only to the exact head that was reviewed** (head-SHA fencing). Otherwise you get the corpus's wedge: a verdict injected into a coder that has already moved on.

### 2.8 How merges are handled
Write-intent fabric first (semantic claims prevent most conflicts before they exist), worktree fallback for destructive scopes, merge queue serializing `MERGING`, `QUARANTINED` findings when conflicts occur. Expanded detail in the prior report §3.2. One addition relevant here: **creative artifacts merge differently.** Binary/derived artifacts (PNG, MP4, GLB) are *never* text-merged — the merge queue takes the artifact whose source-of-record hash is on the winning side, and re-renders. Only the source of record (SVG/Remotion/OpenSCAD/spec) participates in text merge.

### 2.9 Preventing stalling
Taxonomy from agent-swarm `[VERIFIED heartbeat.ts:104-162]` is the best in the corpus and worth restating because it's the thing naive heartbeats get wrong:
- **generic stall** — no progress within threshold
- **no-session stall** — worker clearly dead (no active session at all)
- **stale-heartbeat stall** — session alive but not talking
- plus a **bounded resume budget** so resume loops can't thrash (`RESUME_BUDGET_EXHAUSTED_REASON`)
- plus a **queue-stall alarm that excludes unmet dependencies** — otherwise it cries wolf forever

And the plane's own detectors: no file delta across K turns · repeated identical tool-call signature · token burn over budget with zero commits.

### 2.10 **Making the harness actually finish (the anti-tap-out problem)**

You named the single most under-addressed failure in this whole space: the agent completes 80%, then says "here's what I'd do next" and stops. Nobody in the corpus fully solves it. Pieces exist:

- `no_human` — "a second model in a fresh session reviews each diff and is told to refute 'done'; a tamper guard blocks net test reductions before that review" `[VERIFIED awesome-agent-orchestrators README]`
- `opencode-swarm` — evidence-backed completion gates, completion-verify + drift-verifier gates before phase completion, and a **spec-hash staleness check** `[VERIFIED gate-evidence.ts, spec-hash.ts]`
- ralph-* lineage — "exit detection that recognizes when the work is actually finished"

**Studio's Completion Contract — seven mechanisms, all deterministic except #6:**

1. **Definition of Done is declared at DAG-commit time and is machine-checkable.** Not "implement X" but `assertions: [test:auth/login, lint:clean, file:src/auth.ts exists, scope:auth/*]`. A task with no DoD is not dispatchable. (Corpus counter-signal: iPolloWork ships decorative relations precisely because nothing checks anything.)
2. **`done` is a typed receipt requiring evidence, not a message.** The worker must attach: assertions satisfied + their raw outputs + a file-delta receipt matching the declared write-intent. "I'd suggest next doing Y" is a **`blocked`** receipt with `reason: needs_human | needs_evidence | out_of_scope`, never `done`.
3. **The tap-out detector** is deterministic and fires on the signature of this exact failure: *text proposing future work* + *no assertion satisfied* + *file-delta smaller than the declared scope* → auto-rewind to `in_progress` with a directive: "Assertions X,Y unsatisfied. Continue. Do not propose next steps." Model-free heuristic; no LLM required to catch it.
4. **Scope-completion ratio.** If the declared write-intent says `src/auth/**` and the delta touches 2 of 7 planned files, the ratio is 0.29 and the gate refuses. (This is the immune check applied to *completeness*, not just conformance.)
5. **A tamper guard on the acceptance criteria themselves** (from `no_human`): a worker may not shrink the assertion set. Net test reductions or deleted assertions are rejected before any review runs.
6. **Independent refutation as the last gate.** A fresh model session receives the diff and is explicitly instructed to *refute* the claim of done. This is the only LLM in the completion path, and it is adversarial by construction. `[HYPOTHESIS: an adversarial refute-done reviewer catches ≥30% more incomplete tasks than a same-session self-check, at <15% added token cost on the task.]`
7. **Budgets make tapping out expensive.** A task that stops early *saves nothing* — the assertion gate requeues it under the same budget, so premature exit costs more than finishing.

**The one-line version:** *done is a property of evidence, not of language.*

### 2.11 Prebuilt agent templates — yes, and here's the shape

Yes. This is one of the highest-leverage things Studio can ship, for exactly the two reasons you named:
- **OpenCode / OpenCode Go free model tiers** mean the marginal cost of a specialized agent is near zero *if the configuration already exists*. The friction is authoring, not running.
- **pi / oh-my-pi is deeply customizable** (`ToolLoadMode`, `xd://` mounting, compaction strategy, memory backend, approval tiers) — but that configurability is a wall for new users. `[VERIFIED oh-my-pi tools/types.ts]`

**Templates as `RolePack`s — versioned, composable, lockfile'd:**

```yaml
role_pack:
  id: studio/researcher@1
  role: researcher
  intent: "index, analyze, and synthesize evidence — never write"
  tools:
    allow: [ search.semantic, search.grep, doc.fetch, browser ]
    on_demand: [ git.read, dep.graph ]
    deny: [ fs.write, shell.exec ]
  tool_load_mode: discoverable        # oh-my-pi's mechanism
  harness_profiles:
    opencode:  { model: "free-tier-reasoning", effort: medium }
    pi:        { compaction: shake, memory_backend: mnemopi }
    claude:    { settings_ref: .claude/profiles/researcher }
  completion:
    returns: EvidencePacket
    assertions: [ packet.schema_valid, claims.cited ]
  budget: { max_tokens: 200_000, max_tool_loops: 40 }
```

Ship packs for: `manager` · `researcher` · `coder` · `auditor` · `creative-image` · `creative-video` · `creative-3d` · `qa-web` · `qa-desktop` · `docs` · `release`.

Two ecosystem patterns worth adopting here:
- **Skill lockfiles with pinned revisions** (`skillfold`) — so a RolePack is reproducible.
- **Runbook → SKILL.md compilation** (`agent-runbook`) — so power users author YAML and get portable skills.

And one hard-won rule from opencode-swarm: **derive the tool list from a compile-checked manifest, never a hand-kept list.** v6.48.0 shipped six tools that were listed but never registered. `[VERIFIED opencode-swarm docs/engineering-invariants.md]` RolePacks must pass a registration parity test.

### 2.12 OAuth applications

Two different problems, and conflating them is how local-first apps leak credentials:

**(a) Studio as a client** — the app itself needs GitHub/Slack/Linear/Google.
- Desktop/native: **OAuth 2.0 + PKCE** with loopback redirect (RFC 8252). Device-code flow as fallback for headless/CLI.
- Storage: **OS keychain** (Keychain / Credential Manager / Secret Service) — not an encrypted file next to the DB if you can avoid it. munder-difflin's integration broker is the strong pattern: a loopback capability-token broker where "workers call `127.0.0.1/i/<id>/<path>` with a per-worker handle; the broker injects the real credential upstream; the worker never sees it." `[VERIFIED src/main/integrationBroker.ts]`
- Refresh/rotation lives in the broker, never in agents.

**(b) Agents acting on the user's behalf** — the harder problem.
- **Never give an agent a raw OAuth token.** Give it a **capability handle**: short-lived, scoped to specific API shapes, revocable, attributable to `task_id`.
- iPolloWork has exactly the right taxonomy in its manifest v2 auth methods: `secret-form | oauth-pkce | device-code | hosted-browser` `[VERIFIED packages/types/src/plugins.ts:279-300]`, plus **capability-bound authorization** so a plugin service "cannot address another installation." `[VERIFIED plugin-platform-runtime.ts:37-53]`
- For MCP servers themselves, the **MCP authorization spec** is the right seam: the gateway holds tokens; agents call the gateway; the gateway attaches credentials.
- Every OAuth'd write is a **one-shot approval fact** (opencode-swarm `WriteApprovalFactV1`: session/action/content-bound, consumed-once) so a compromised agent can't replay an authorization.

### 2.13 Can Codex or Claude support multiple profiles and agents?

**Yes. The mechanism is verified and it is `CLAUDE_CONFIG_DIR`.**

- "Each profile is a complete, isolated Claude Code configuration directory (settings, credentials, MCP servers, CLAUDE.md, history — everything)." `[VERIFIED github.com/quinnjr/claude-code-profiles]`
- "Run two Claude Code accounts simultaneously on macOS without re-authenticating by using separate configuration directories." `[VERIFIED gists: bitclaw, KMJ-007]`
- The multi-account tooling (`ccm`) states the out-of-box pain exactly: "If you have two Anthropic accounts — company and personal — switching means logging out and back in, and everything else (plugins, MCP, history) stays mixed. ccm fixes that with the official CLAUDE_CONFIG_DIR mechanism." `[VERIFIED github.com/CarlosTheory/claude-multi-account]`
- direnv-based per-folder profile switching is a documented pattern. `[VERIFIED dev.to/ashishxcode]`

**This is not merely possible — the corpus already treats it as the isolation knob.** `agent-of-empires` pins `CLAUDE_CONFIG_DIR` in its spawn env-deny matrix specifically so a child agent cannot migrate its identity. `[VERIFIED src/acp/acp_client/spawn.rs:86-90]`

**Studio's model — Profile-as-Code:**
| Dimension | Mechanism |
|---|---|
| N accounts on one machine | N × `CLAUDE_CONFIG_DIR` (one per agent identity) |
| N permission sets | separate `settings.json` per profile + gateway role manifest |
| N MCP tool surfaces | per-profile MCP config, *or* one shared gateway with per-agent capability tokens (preferable — one place to enforce) |
| Codex side | `auth.json` / profiles per config dir; `LocalCliCapabilities` describes resume + permission policy per harness `[VERIFIED Orkas local_agents/registry.ts:37-80]` |
| Rate limits | **shared per account** — N agents on one account multiply throttling. Budget arms must be per-account, not per-agent. |
| Gotchas | lock files in a shared config dir; transcript paths keyed by cwd (munder-difflin works around this by seeding transcripts per target cwd `[VERIFIED transcript.ts:63-85]`) |

**Answer to "can Codex or Claude even support multiple profiles and agents?"** — yes, cleanly, via config-dir isolation; Claude Code more maturely than Codex. Orkas abstracts the difference behind `resume: 'native' | 'session-id' | 'none'` and `LocalCliPermissionPolicy`. Studio should adopt that contract and not care which harness it's talking to.

## 3. Dialectic — Thesis / Radical Antithesis / Synthesis

### 3.1 THESIS — Wild Proponent

Studio is a **full-spectrum creative software agency**: a human describes a goal — "ship the landing page, the product video, the 3D hero asset, the app onboarding flow, and the docs" — and the Manager decomposes it into a DAG spanning code, image, video, 3D, browser, and desktop lanes. Researchers gather evidence into cited packets. Creative agents produce editable artifacts. Coders wire it together in isolated worktrees. Auditors gate every merge and every render. A vector memory remembers every decision across months. Agents hold OAuth handles to GitHub, Figma, Linear, and Slack. A War Room shows the DAG, the token burn, and the live render previews. A phone app lets you approve and steer from anywhere. Prebuilt RolePacks mean a user with a free OpenCode tier gets a nine-agent agency on day one. The whole thing runs locally, finishes what it starts, and costs less in coordination than the work it coordinates.

### 3.2 RADICAL ANTITHESIS — Paradigm Inverter

**I1 — INVERSION: The "agency" is the wrong unit.** What humans actually want is *artifacts that ship*, not a fleet. Invert the product: **Studio is an artifact compiler with a review gate.** Agents are an implementation detail of the compiler's backend. The UI shows the artifact lineage, not the org chart. (Corpus signal: munder-difflin's avatar floor is *delight*; iPolloWork's project view is *org chart*. Neither shows artifact lineage.)

**I2 — SUBTRACTION: Remove the vector database entirely.** See §2.4 — L0–L3 (git + receipts + SQL + markdown) answer most queries. The vector index is where "complicated" lives: stale embeddings, rebuild costs, model-version drift, and the 100GB class of leak munder-difflin actually hit. *Ship without L4 and see if anyone misses it.*

**I3 — SUBTRACTION: Remove the creative generator from the agent loop.** Generative video/3D is slow, expensive, and non-deterministic. What if creative agents only ever write **source of record** (SVG/Remotion/OpenSCAD/HTML), and a **separate deterministic render farm** produces pixels? The agent never waits on a video model. Cost becomes predictable; iteration becomes free; the "does it finish?" problem largely evaporates for creative work.

**I4 — ADJACENT DOMAIN (journalism): The Evidence Packet is a citation, and citations have standards.** Journalism and academia solved "prove it" centuries ago. Borrow the **footnote + retractions** model: claims are durable, citations are locators, and *retractions are first-class* (`superseded_by`). The researcher's reputation is measurable: citation density and retraction rate. That's a real incentive, not a prompt instruction.

**I5 — ADJACENT DOMAIN (CI/CD): "Done" is a green pipeline, not a message.** The CI world already solved completion discipline: a PR is merged when checks are green, and "here's what I'd do next" is not a state. Studio's task state machine should be modeled on **checks**, not on conversation. Tap-out becomes structurally inexpressible — there is no `done` without `checks_passed`.

**I6 — ADJACENT DOMAIN (markets): Sell the templates, give away the runner.** The free models (OpenCode Go tier) make the *runtime* nearly free. The scarce asset is **knowing how to configure a good agency** — the RolePacks. Invert the business: the orchestration engine is open; RolePacks + premium creative connectors are the product.

**I7 — COUNTER-INTUITION: Don't parallelize creative work — serialize it and parallelize *critique*.** Creative iteration is a hill-climb; five parallel video drafts produce five mediocre videos. One video with five parallel *reviewers* (taste, brand, accessibility, copy, technical) produces one good video. This is the opposite of Orkas' "nine specialists in parallel" and it's probably why those outputs need human cleanup.

**I8 — INVERSION: The desktop/web automation agent is a *testing* agent, not an *operating* agent.** Driving a real desktop app in production is a reliability tar pit. Use the accessibility tree to drive apps **only for QA and evidence capture** ("does the onboarding actually work?"), never as a delivery mechanism. When something must be automated for real, generate code (Playwright/AX script) and keep it — don't re-derive it every run.

**I9 — SUBTRACTION: Remove "human feedback from UI" as a general problem.** You don't need general human feedback. You need three decisions: **scope, budget, taste.** Everything else is an assertion the machine can check. Design the entire feedback surface around those three, and delete the chat-with-every-agent affordance.

### 3.3 SYNTHESIS — Portfolio Builder

#### A. Novel Feature Vectors (5)

**FV1 — Completion Contract (anti-tap-out)**
*Pitch:* `done` is a typed receipt requiring machine-checkable evidence; proposing next steps is a `blocked` receipt; a deterministic tap-out detector rewinds the task; a tamper guard forbids shrinking acceptance criteria; an adversarial second model refutes the claim of done.
*Why now:* nobody in the corpus or the community conversation solves this, and it's the difference between a demo and a system. CI solved it in 2010; agents regressed to chat.
*Falsification probe:* `[HYPOTHESIS: across 30 mixed tasks, the Completion Contract cuts the "stopped early + suggested next step" rate from a baseline of >40% to <10%, at <20% added token cost per task.]`

**FV2 — Evidence Packets (the find↔return contract)**
*Pitch:* Researchers return content-addressed, citation-bearing `EvidencePacket`s (claims + verbatim quotes + blob refs + open questions), never prose. Implementers read `evidence://` refs. The zero-token plane moves packets and cannot summarize.
*Why now:* claude-smart's cite-bar proves the "was this used?" loop is buildable; content-addressed blobs are already in the plan for receipts.
*Falsification probe:* `[HYPOTHESIS: implementers working from EvidencePackets produce changes grounded in source evidence ≥2× more often than implementers working from prose summaries, measured by auditor citation-verification rate.]`

**FV3 — Artifact-First Creative Lanes**
*Pitch:* Creative agents write only *source of record* (SVG/HTML/CSS, Remotion, OpenSCAD, PPTX source); a deterministic render farm produces pixels. Binary artifacts never text-merge — the merge queue re-renders from the winning source hash.
*Why now:* the editable-output paradigm is converging across iPolloWork and Orkas; the missing piece is *separating authoring from rendering* so agent iteration is free and fast.
*Falsification probe:* `[HYPOTHESIS: authoring-then-rendering reduces median iteration time per creative revision by ≥5× versus direct generative output, with human preference scores no worse in blind A/B.]`

**FV4 — Profile-as-Code**
*Pitch:* An agent's identity is a versioned manifest: `CLAUDE_CONFIG_DIR` (or harness equivalent) + settings + role manifest + capability-token broker handles. N agents, N identities, one declarative file. Rate-limit budgets are per-account.
*Why now:* `CLAUDE_CONFIG_DIR` isolation is verified and widely used by hand; nobody productizes it. AoE already pins it as the identity boundary.
*Falsification probe:* `[HYPOTHESIS: 5 concurrent agents on 2 accounts with Profile-as-Code show zero credential cross-talk in an adversarial probe suite and correct per-account rate-limit accounting, with setup under 2 minutes.]`

**FV5 — Memory Ladder (structured-first, vector opt-in)**
*Pitch:* L0 git/receipts → L1 SQL+FTS → L2 markdown → L3 lifecycle memory rows → L4 optional semantic index with mandatory reranker. L4 is per-project opt-in, versioned, re-derivable.
*Why now:* the community evidence says vector-as-architecture is a trap; the corpus's best memory (oh-my-pi `MemoryRow`) is lifecycle-based, not vector-based.
*Falsification probe:* `[HYPOTHESIS: L0–L3 answer >70% of agent memory queries correctly on a 30-day project; L4 adds <10% end-task success while costing measurable indexing time and storage.]`

#### B. Lateral Architectural Moves (3)

**LM1 — Vector-first memory → Ladder memory (L4 opt-in)**
- *Current:* "add memory" guides open with a vector DB.
- *Lateral:* git + SQL + markdown as the substrate; embeddings only where paraphrase genuinely matters, behind a reranker.
- *Trade-off:* lose one-shot "semantic search everything"; gain no indexing drift, no rebuild cost, no 100GB leak, and `grep`-speed answers.
- *Migration spike:* implement L0–L3 only; instrument every memory query for a week; measure hit rate without L4.

**LM2 — Prose research reports → Evidence Packets**
- *Current:* researcher writes a summary; implementer reads it.
- *Lateral:* typed packet with citations and content-addressed blobs; prose is decoration.
- *Trade-off:* more structure on the researcher, slightly slower return; gain groundability and auditor-verifiable provenance.
- *Migration spike:* define `EvidencePacket` schema + `evidence://` reader; run one research→implement pair both ways; measure auditor citation-verification rate.

**LM3 — Screenshot computer use → Accessibility-tree first (pixels as fallback)**
- *Current:* vision computer use as the general desktop answer.
- *Lateral:* AXUI/UIA/AT-SPI structured trees; generate and keep automation code; pixels only for canvas/legacy.
- *Trade-off:* less general (fails on pure canvas apps); far more reliable and far cheaper in tokens.
- *Migration spike:* one real desktop app, same 10 interactions, both methods; compare success rate, token cost, and wall time.

#### C. Experimental Hypotheses (3) — each a spike of < 1 day

1. `[HYPOTHESIS: The Completion Contract reduces the "stopped early and suggested next steps" rate from >40% to <10% across 30 mixed tasks, with <20% added token cost per task. Kill criterion: reduction <15 points, or added cost >40%.]`
2. `[HYPOTHESIS: Implementers given EvidencePackets ground their changes in source evidence at ≥2× the rate of implementers given prose summaries, per auditor citation-verification. Kill criterion: ratio <1.3×, or researcher completion time more than doubles.]`
3. `[HYPOTHESIS: Memory Ladder L0–L3 answers >70% of agent memory queries on a multi-week project without any embedding index. Kill criterion: <50% hit rate, which would justify building L4 immediately.]`

**Rejected convergence options** (explicitly not recommended): "ship vector-first and add structure later" (you'll never add it); "let the researcher write a summary *and* a packet" (the summary will be what gets read); "detect tap-out with another LLM call" (it's a deterministic signature — don't spend tokens); "one universal creative agent" (conflating source-of-record formats is how you lose editability).
